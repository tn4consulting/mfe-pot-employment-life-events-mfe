# mfe-pot-life-events-mfe

## What this is

The **multi-life-event guided journey** frontend for the mfe-pot Government of Canada MFE proof-of-technology — one federated remote hosting several parametric life-event journeys (`job-loss` today; `birth`/`disability` added to prove the pattern generalizes; `death`/`caregiving` follow the same shape when built), each stitching `mfe-pot-job-bank-mfe`, `mfe-pot-employment-insurance-mfe`, and `mfe-pot-dashboard-mfe` together into one narrative rather than presenting them as separate benefit programs. Federated as a remote into `mfe-pot-msca-shell`, mounted at `/life-events/:lifeEventId`. Renamed 2026-08 from `mfe-pot-employment-life-events-mfe` (repo, federation identity, everything) when this generalization landed — see `mfe-pot`'s own `docs/plans/` for the design. Also embeds cross-remote widgets (dashboard's payment history, job-bank's applications, employment-insurance's reporting status) host-mediated via `mfe-pot-msca-shell` — see the platform repo's CLAUDE.md "Federation" section.

## What's in this repo

- `apps/life-events-mfe` — the only app; frontend-only, federated on port `4202` in local dev. No co-located BFF — there's no distinct bounded context here that justifies its own backend. Repo directory, Nx project, federation identity (`federation.config.mjs`'s `name`), Docker image, and Helm chart/release are all named `life-events-mfe`. The underlying business-domain naming (Nx `scope:life-events` tag, CMS content keys) deliberately stays un-suffixed — that's domain identity, not hosting identity. `apps/life-events-mfe/src/app/*.tsx` holds every component directly — no separate `libs/<name>/feature-*` library (see the platform repo's CLAUDE.md, "Components live in the app"). **All 5 life events share one remote, not one remote each** — see "The life-events kit" below for why and how.
- `charts/life-events-mfe` — depends only on the platform repo's `mfe-frontend-lib` (no BFF, so `mfe-backend-lib` isn't used), same shape as either shell's chart.

Depends on published packages from GitHub Packages: `@tn4consulting/shared-auth`, `shared-content-client`, `shared-federation-config`, `shared-federation-runtime` (**`^2.0.0`** — see below), `shared-i18n`, `shared-locale-sync`, `shared-runtime-config`, `shared-ui-scds-core` (pinned in `package.json`; keep in sync with `platform-versions.json` in `mfe-pot-platform`).

## The life-events kit

Each life event is an ordinary React page component, not data dispatched through a generic schema/renderer — that model (a `LifeEventDefinition` object with a `kind`-discriminated `sections` array, and `kit/LifeEventPage.tsx` switching on `kind`) was tried and deliberately abandoned (2026-08): 2 of the first 3 life events needed the schema's `'custom'`/`leadingItem` escape hatch for real content anyway, leaving only `birth` as a genuinely "pure data" example — the schema's generality was mostly overhead, not payoff. `src/app/kit/` now holds reusable *helper components* pages call directly as JSX, plus a small authoring vocabulary, so a new life event is still cheap to author consistently, but without a data layer standing between authoring and what renders:

- `kit/bilingual-content.ts` — `BilingualText { en, fr }` + `text(value, locale)`, `StaticChecklistItem`, `ServiceLink`. Plain, reusable authoring types; no `LifeEventDefinition`/`kind` union.
- `kit/ChecklistSection.tsx` (`{ id, heading, items, leadingItem? }`), `kit/ServiceLinksSection.tsx` (`{ heading, links }` — an `scds-card` grid), `kit/WidgetSlot.tsx` (`{ widgetId, heading? }` — a cross-remote widget by id, see below) — the reusable renderers a page composes directly. All three self-serve `useLocale()`/`useTranslations()` rather than taking translated strings as props (React has no per-bundle DI-singleton-identity concept for two `useTranslations()` call sites to collide over, unlike the pre-migration Angular version — see `App.tsx`'s own comment for the historical reason this repo used to thread labels through props instead).
- `kit/LifeEventLayout.tsx` — the one piece of chrome every page shares: `{ lifeEventId, contentClient, children }`, fetches and renders this life event's CMS intro block (keyed by convention as `life-events.<id>.intro`), then renders `children`. Centralizes what used to be `App.tsx`'s own fetch effect. Everything below the intro is fully free-form per page — this wrapper imposes no other shape, and nothing requires a page to use it.
- `pages/<Id>Page.tsx` (`JobLossPage.tsx`, `BirthPage.tsx`, `DisabilityPage.tsx`) — **the actual authoring surface**. Each is a real component wrapping its content in `<LifeEventLayout>` and composing `ChecklistSection`/`ServiceLinksSection`/`WidgetSlot`/any bespoke component directly as JSX — no `kind`/`render()` indirection. `pages/index.ts` builds the `lifeEventId → Component` registry `App.tsx` looks up, throwing at module-load time on a duplicate id (the one automated safety net left, now that there's no schema to deep-validate).
- `JobSearchChecklistItem.tsx`/`EiChecklistItems.tsx` are `job-loss`'s own bespoke content, rendered directly by `pages/JobLossPage.tsx` alongside its kit-driven sections — not part of the generic kit itself.

**Adding a life event**: add one `pages/<Id>Page.tsx`, register it in `pages/index.ts`, add its intro copy to `content-client.ts`'s static fallback (and Strapi's seed data), and — only if it uses a widget id no other life event has already registered — add one entry to the shell's widget registry (`mfe-pot-msca-shell`'s `routes.tsx`). No other file in this repo or the shell should need to change.

## Generic widget loading (`shared-federation-runtime@2.0.0`)

Widgets are loaded by a plain string id (`useWidgetLoader('payment-history')`, `WidgetSlot`'s own internal call) resolved against a registry the shell provides via `WidgetRegistryContext` — **not** one hand-written Context+hook pair per widget type, which is how this repo worked before this generalization (`usePaymentHistoryWidgetLoader()`/`useJobApplicationsWidgetLoader()`/`useEiReportingStatusWidgetLoader()` no longer exist in `shared-federation-runtime`; `2.0.0` is a breaking major for exactly this reason). `useWidgetLoader` degrades gracefully to `undefined` — never throws — both when there's no host at all (this remote running standalone, `nx serve`/tests) and when a host exists but hasn't registered the requested widget id, matching the family's "every app independently testable" requirement. If a widget's loader never resolves, check `mfe-pot-msca-shell`'s `routes.tsx` (`WIDGET_REGISTRY` constant and the `WidgetRegistryContext.Provider` wrapping the life-events route) before assuming the bug is here — and specifically check whether that repo's own `build.mjs`/`serve.mjs` correctly marks `@tn4consulting/shared-federation-runtime` as `external`, the same silent-degrade gotcha documented in the platform repo's CLAUDE.md for the pre-generalization version of this mechanism.

## Repo-specific things worth knowing

- **`App.tsx` takes `lifeEventId` as a plain prop, not a router param it reads itself** — `react-router-dom` isn't a federation-shared singleton, so this remote's own bundled copy has a different Context identity than the shell's; `useParams()` here would silently resolve to nothing. The shell reads its own `/life-events/:lifeEventId` param and forwards it via `RemoteRouteHost`'s `props` (`shared-federation-runtime@2.0.0` added prop-forwarding support specifically for this). Defaults to `'job-loss'` so `nx serve` standalone (no shell, no route) still renders something. `App.tsx` itself only does the claim check and bootstraps `ContentClient`, then looks the id up in `pages/index.ts` and renders that page — the CMS intro-fetch chrome lives in `kit/LifeEventLayout.tsx`, not here.
- **`src/runtime-config.ts` and `public/env.js`** exist for `ContentClient`'s `strapiBaseUrl` — this app fetches each life event's own CMS-driven intro block the same way `mfe-pot-dashboard-mfe`/`mfe-pot-job-bank-mfe`/`mfe-pot-employment-insurance-mfe` do. `charts/life-events-mfe/values.yaml`'s `frontend.runtimeConfig.strapiBaseUrl` points at `mfe-pot-platform`'s `charts/strapi` (`http://cms.mfe-pot.local`, browser-to-server, not in-cluster Service DNS).
- **`federation.config.mjs`'s `exposes` map (`./Component`) must point at `apps/life-events-mfe/...`** — a stale path here fails the federation build with `FsPath ... does not exist` (the platform repo's CLAUDE.md documents this gotcha generally).
- **The job-search and EI checklist items derive real completion state, not a self-reported guess** — `JobSearchChecklistItem.tsx` passes an `onApplicationsLoaded` callback prop into job-bank's mounted `JobApplicationsList`, and `EiChecklistItems.tsx` passes `onStatusLoaded` into employment-insurance's `ReportingStatus` (both added in their respective repos specifically for this). Both widgets mount as soon as their loader resolves — not gated behind the "complete" check — specifically so their own fetch effect runs and the callback fires; only their visual detail is hidden (via inline `display: none`, not unmounted) until there's something real to show.
- **The checklist itself renders as `scds-checklist`/`scds-checklist-item`** (`@tn4consulting/shared-ui-scds-core`) — a presentational-only pair with no completion state of its own; the interactive control inside each item (a native checkbox for self-reported items, a `scds-link` that becomes a status link once complete) is slotted in as plain children.
- **The shell route this app is reached through is `/life-events/:lifeEventId`** (previously the single-life-event `/job-loss` route) — see `mfe-pot-msca-shell`'s own CLAUDE.md/`routes.tsx`. `mfe-pot-platform`'s `apps/mfe-e2e` specs were updated to match.
- **CI** (`.github/workflows/ci.yml`): lint/test/build, then builds the image, spins up an ephemeral `kind` cluster, `helm install`s this chart, and curls the Ingress-routed hostname to confirm it serves. See `README.md` for local install/serve/build/Docker/Helm instructions.
